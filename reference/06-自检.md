## 【第二步：逐条自检】

**规则：每条必须给「通过 / 不通过 + 具体证据」。**
不许笼统说「已完成」「没问题」。没真的验证过的一律标「未验证」，
**谎报通过比暴露问题严重得多。**

### 一、功能闭环（对照所有子 PRD 的交互元素表）
- [ ] 每个子 PRD 的交互元素表逐行走一遍，全部有真实响应
- [ ] 不存在任何点了没反应的元素
- [ ] 不存在 `alert('待开发')`、`TODO`、`console.log` 占位
- [ ] 不存在跳转到空白页或死链的入口
- [ ] 所有表单都有校验，非法输入有明确提示

### 二、状态完整性
对每个会发请求或改数据的功能，确认五种状态都做了：
- [ ] 空态（没数据时界面什么样，有没有引导）
- [ ] 加载中（有 loading，且不会让用户重复点击）
- [ ] 成功
- [ ] 失败（错误信息可读，有重试入口，不是一行英文报错）
- [ ] 断网 / 服务不可用（尤其记忆层，必须能降级）

### 三、记忆层专项（seemem）
- [ ] 所有请求走统一封装，且**检查了响应体 `code` 字段**而非只看 HTTP 200
- [ ] `/summary` 超时 ≥ 60s，`/save`（同步模式）≥ 90s
- [ ] 鉴权是 `Authorization: Bearer <token>`，**没有传租户 ID**
- [ ] `user_id` 在每个接口都显式传了（POST 在 body，GET/DELETE 在 query）
- [ ] 记忆服务挂掉时能降级成普通对话继续可用，不白屏
- [ ] 用户能在界面上**感知到**记忆在起作用，而不只是后台默默调用
- [ ] **已实际跑通一次「写入 → 等待 → 召回命中」完整链路，并贴出实际返回**

### 四、DeepSeek 对话专项
- [ ] 调用地址、key、model 与 P0 的 CONFIG 一致
- [ ] 流式输出正常，中断/超时有处理
- [ ] API 报错（余额不足、限流、超时）有可读提示，不是白屏或静默失败
- [ ] 长对话不会无限增长 token（有截断或摘要策略）

### 五、设计一致性
- [ ] 全项目无硬编码的颜色/阴影/圆角值，全部走 DESIGN.md 的 CSS 变量
- [ ] 与 `design-preview.html` 对照，实际界面和设计规范一致
- [ ] 深色模式（若做了）所有文字对比度足够
- [ ] 动效统一，没有某些地方有过渡、某些地方生硬跳变
- [ ] 按 `web-design-guidelines` 过一遍无障碍：焦点可见、可键盘操作、对比度达标

### 六、响应式与兼容
- [ ] 375px 宽度下无横向滚动条、无元素重叠、无文字截断
- [ ] 桌面宽屏下内容不会被拉伸得难看
- [ ] 长文本、超长用户名、大数字都不撑破布局（**用极端值实际测一次**）
- [ ] 控制台无报错、无警告

### 七、数据可信度
- [ ] mock 数据像真的（真实中文姓名、合理时间、有波动的数值）
- [ ] 没有「测试1/测试2」「Lorem ipsum」「示例数据」这类穿帮内容
- [ ] 时间格式统一，数字有千分位，金额有单位

### 八、演示可靠性（最容易忽略，但现场最致命）
- [ ] 从零完整走一遍主流程，全程无卡顿无报错
- [ ] **记忆召回的演示数据已提前预热写入**（召回有数秒到数分钟延迟）
- [ ] **断网情况下打开，界面仍能渲染**（不依赖任何外部 CDN）
- [ ] 刷新页面后状态处理正确（该保留的保留，该重置的重置）
- [ ] 准备好了 API 失败时的话术和兜底演示路径
